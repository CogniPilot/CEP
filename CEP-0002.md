# CEP-0002: Platform Repository Restructuring

| Field | Value |
|-------|-------|

| Title | Platform Repository Restructuring |
| Author | CogniPilot Maintainers |
| Status | Draft |
| Type | Standards Track |

## Abstract

This CEP proposes restructuring the CogniPilot repositories to eliminate duplication and make everything platform-specific. The current architecture shares configurations across platforms, creating risk when frequently-updated platforms cause regressions in stable ones. Under this proposal, all ZROS driver code from Cerebri and Spinali consolidates into zros_drivers. Helmet organizes by platform with SHA-locked dependencies. Cerebri contains self-contained platform folders, each with its own west.yml, using a symlink method to swap manifests without re-downloading Zephyr. Cranium splits into two ROS packages per platform: robot (hardware) and desktop (simulation). Modelica models live alongside their generated control code, with contributors responsible for regeneration. Poetry is removed from builds entirely. This structure isolates platforms from each other while maintaining efficient resource sharing through the west symlink mechanism.

## Motivation

The current CogniPilot architecture shares base configurations across platforms. This creates several problems:

1. **Cascading breakage**: When a frequently-updated platform modifies shared code, stable platforms that haven't been tested recently may break unexpectedly.
2. **Testing burden**: Every shared change requires re-validating all platforms, which is impractical given limited flight-testing resources.
3. **Version coupling**: Platforms cannot pin to known-good dependency versions independently.
4. **Driver fragmentation**: ZROS driver code is scattered across Cerebri and Spinali, causing duplication and version mismatches.
5. **Build complexity**: Poetry adds unnecessary complexity to the build process.

Platforms have different release cadences and testing requirements. A rover updated weekly shouldn't destabilize a quadcopter that was flight-tested months ago. This CEP addresses these issues by making each platform fully self-contained while preserving efficient resource sharing.

## Specification

### Helmet

Helmet restructures to be purely platform-specific with SHA-locked dependencies pointing to last validated tests:

```
helmet/
  platforms/
    <platform_name>/
      <platform_name>_desktop.yaml
      <platform_name>_robot.yaml
```

### zros_drivers

All ZROS driver-related code currently scattered across Cerebri and Spinali shall be consolidated into zros_drivers. This makes zros_drivers the single source of truth for driver implementations, simplifying dependencies and reducing duplication.

### Cerebri

Each platform is self-contained with its own west.yml. The west symlink method traverses `cerebri/spinali` subfolders automatically without requiring explicit platform names, enabling manifest swaps without re-downloading Zephyr (tested at <15ms vs ~60s for full reclone):

```
cerebri/
  b3rb/
    west.yml
    ...
  melm/
    west.yml
    ...
  rdd2/
    west.yml
    prj.conf
    Kconfig
    CMakeLists.txt
    src/
      dream/              # Platform-specific simulation hooks
      control/
        model.mo          # Modelica source
        model_gen.c       # Generated control code
      topics.h            # Auto-generated from zros_drivers + platform code
    boards/
      posix
      real_board_(.conf/.overlay)
```

- **Modelica**: Models live with generated code. Contributors modifying `.mo` files must regenerate control code.
- **Topics**: `topics.h` derived from selected zros_drivers and platform-specific code.
- **Build**: Poetry removed. Control code generation is a separate step from Zephyr image builds.

### Cranium

Two ROS packages per platform:

- **platform_robot**: nav2 configs, URDF, real hardware launch scripts with device references
- **platform_desktop**: simulation/visualization, depends on robot package, includes RViz layout for Electrode

Desktop does not use robot launch scripts (those reference real hardware, not simulation).

### Electrode

Shared plugins only. No platform-specific code.

### Adding a New Platform

```
cerebri/
  <new_platform>/

cranium/
  <new_platform>_desktop/    # Include electrode node in dedicated launch script
  <new_platform>_robot/
```

## Rationale

**Why consolidate drivers into zros_drivers?** Driver code is currently fragmented across Cerebri and Spinali, leading to duplication and version mismatches. A single authoritative location simplifies maintenance and ensures consistent driver behavior.

**Why platform-specific west.yml files?** Each platform can pin exact dependency versions that were flight-tested, independent of other platforms. This prevents untested version combinations.

**Why the symlink method?** Testing showed platform switches complete in <15ms compared to ~60s for full reclones. This preserves the efficiency of a shared workspace while providing isolation.

**Why remove Poetry?** Poetry adds build complexity without proportional benefit. Separating control code generation from Zephyr builds simplifies the toolchain.

**Why Modelica alongside generated code?** Keeping model source and generated code together ensures they stay in sync. Making the contributor responsible for regeneration prevents stale generated code.

**Why two Cranium packages per platform?** Desktop and robot have fundamentally different launch requirements (simulation vs real hardware). Separating them avoids conditional logic and makes dependencies explicit.

## Backwards Compatibility

This restructuring is not backwards compatible. Existing workflows will require migration:

- **Helmet users**: Must adopt the new platform-based directory structure
- **Cerebri/Spinali developers**: ZROS driver code moves to zros_drivers; platform code moves into platform-specific folders with individual west.yml files
- **Cranium packages**: Must be split into platform_robot and platform_desktop variants
- **Build scripts**: Any scripts using Poetry must be updated

Migration guides will be provided. The restructuring can be phased per-platform to reduce risk.

## Reference Implementation

Implementation will proceed in phases:

1. Consolidate all ZROS driver code from Cerebri and Spinali into zros_drivers
2. Restructure Cerebri with platform-specific west.yml files and symlink mechanism
3. Migrate Helmet to platform-based layout with SHA-locked dependencies
4. Split Cranium packages into robot/desktop variants
5. Remove Poetry from build system
6. Update documentation and migration guides

Links to implementation PRs will be added as work progresses.
