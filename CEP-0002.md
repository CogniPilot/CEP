# CEP-0002: Vehicle Repository Restructuring

| Field | Value |
|-------|-------|
| CEP | 0002 |
| Title | Vehicle Repository Restructuring |
| Author | CogniPilot Maintainers |
| Status | Draft |
| Type | Standards Track |
| Created | 2026-01-20 |

## Abstract

This CEP proposes restructuring the CogniPilot codebase by separating vehicle applications into individual repositories and refocusing Cerebri as a pure middleware layer. The goal is to reduce testing burden, improve maintainability, and allow vehicles to operate on stable, flight-tested middleware versions while the middleware continues to evolve independently.

## Motivation

### Current Architecture Problems

The current CogniPilot architecture has evolved in a way that creates several maintenance and testing challenges:

1. **Cerebri's Role Has Drifted**: Cerebri was originally intended to be a ZROS/Zephyr middleware layer enabling driver communication with the Zephyr operating system. However, it has accumulated vehicle application code in an `app/` folder, blurring the line between middleware and application.

2. **Unnecessary Repository Fragmentation**: The `zros_drivers` repository was created to hold ZROS drivers, but this separation from Cerebri adds complexity without clear benefit. The drivers and middleware are tightly coupled and should evolve together. Meanwhile, Cerebri itself has become effectively just an application folder with some remaining driver code.

3. **Testing Burden is Unsustainable**: Flight testing time is a scarce resource. The current monolithic structure means that every change to the middleware or Zephyr version potentially affects all vehicles, but there isn't sufficient time to flight-test every vehicle on every change. This creates risk and slows development.

4. **Version Coupling**: All vehicles are forced to track the same version of the middleware. When the middleware changes, vehicles that were previously flight-tested may regress, and there's no easy way to maintain a known-good configuration.

5. **CI Failures Block Unrelated Work**: If a vehicle's CI fails due to middleware changes, it can block unrelated development even though the failure may simply indicate the vehicle needs updating (not that anything is fundamentally broken).

### The Core Problem

The fundamental issue is that **vehicle application code and middleware code have different release cadences and testing requirements**:

- **Middleware** can be tested through automated CI and basic hardware validation
- **Vehicles** require actual flight testing to validate safety-critical behavior

Mixing these in a single repository forces a choice between:
- Slow middleware development (waiting for all vehicles to be flight-tested)
- Risky vehicle releases (shipping code that hasn't been flight-validated)

Neither option is acceptable.

## Specification

### Repository Structure

The proposed structure separates concerns into distinct repositories:

```
cognipilot/
├── cerebri/              # Pure middleware layer (includes ZROS drivers)
├── synapse_ros/              # Communication bridge to ROS
├── spinali/              # Connected sensors and actuators with Zephyr RTOS
├── cerebri-b3rb/         # B3RB vehicle application
├── cerebri-rdd2/         # RDD2 vehicle application
├── cerebri-melm/         # MELM vehicle application
└── ...                   # Additional vehicle repositories
```

Note: Spinali currently depends on `zros_drivers` and shall be updated to depend on Cerebri once the driver consolidation is complete.

### Cerebri as Pure Middleware

Cerebri shall be refocused as a middleware layer with the following responsibilities:

1. **ZROS Communication**: Provide the ZROS publish/subscribe infrastructure
2. **ZROS Drivers**: All ZROS drivers (currently in `zros_drivers`) shall be reabsorbed into Cerebri
3. **Zephyr Integration**: Bridge between ZROS drivers and Zephyr OS services
4. **Common Utilities**: Shared utilities used across vehicle applications
5. **Hardware Abstraction**: Common interfaces for interacting with hardware through ZROS

The `zros_drivers` repository shall be merged back into Cerebri. Maintaining a separate repository for drivers adds unnecessary complexity, as the drivers and middleware are tightly coupled and should be versioned together.

Cerebri shall NOT contain:
- Vehicle-specific application logic
- Vehicle configuration files
- Vehicle-specific parameters or tuning

### Vehicle Repositories

Each vehicle shall have its own repository containing:

1. **Application Code**: Vehicle-specific control logic, state machines, and behavior
2. **Configuration**: Vehicle parameters, tuning values, and board configurations
3. **Documentation**: Vehicle-specific setup, operation, and maintenance guides
4. **CI Configuration**: Vehicle-specific continuous integration

Each vehicle repository shall:
- Declare its middleware dependencies (Cerebri version, Zephyr version, etc.)
- Declare the onboard firmware version it was flight-tested with
- Declare ZROS topics on a per-vehicle basis, based on enabled drivers and vehicle requirements
- Be able to pin to specific versions of dependencies
- Maintain its own release cadence independent of middleware

### Topic Declaration

ZROS topics shall be declared on a per-vehicle basis rather than globally in the middleware. This approach:

1. **Reduces memory footprint**: Only topics required by the vehicle are instantiated
2. **Enables driver-based configuration**: Topics are enabled/disabled based on which drivers are configured for the vehicle
3. **Improves modularity**: Vehicles only include the communication channels they actually use
4. **Simplifies testing**: Each vehicle's topic set is explicit and testable

The topic declaration mechanism shall be part of the vehicle's build configuration, allowing compile-time determination of the required topic set.

### Minimal Reference Application

Cerebri shall include a minimal reference application that:

1. **Validates Core Functionality**: Tests that ZROS communication works correctly
2. **Tests Synapse Bridge**: Validates communication with ROS through Synapse
3. **Runs on Supported Boards**: Provides hardware validation for each supported board
4. **Serves as Documentation**: Acts as an example for vehicle developers

This minimal application shall be:
- Tested in CI on every middleware change
- Tested on hardware for supported boards
- Simple enough that hardware testing doesn't require flight testing

### Continuous Integration Strategy

#### Middleware CI (Blocking)

The Cerebri middleware CI shall:
- Run on every pull request and merge to main
- Test the minimal reference application
- Validate compilation for all supported boards
- Run unit tests and integration tests
- **Block merges on failure**

#### Vehicle CI (Non-Blocking Warnings)

Vehicle repositories shall have daily CI runs that:
- Attempt to build against the latest middleware
- Report compatibility status
- **Generate warnings, not failures**, when builds break

This approach acknowledges that:
- Middleware will evolve faster than vehicles can be flight-tested
- A vehicle not building on latest middleware isn't necessarily broken
- The vehicle maintainer will update when they're ready to flight-test

#### Flight Test Requirements

For vehicle repositories:
- **Main branch shall contain only flight-tested code**
- Pull requests to main shall require flight test validation
- Flight test results shall be documented in the PR

### Dependency Management

Vehicle repositories shall use a dependency manifest (e.g., `west.yml` for Zephyr) that specifies exact versions:

```yaml
# Example vehicle west.yml
manifest:
  remotes:
    - name: cognipilot
      url-base: https://github.com/cognipilot
    - name: zephyrproject
      url-base: https://github.com/zephyrproject-rtos

  projects:
    - name: zephyr
      remote: zephyrproject
      revision: v3.5.0
      import: true
    - name: cerebri
      remote: cognipilot
      revision: v2.1.0  # Pinned to flight-tested version (includes ZROS drivers)
```

Each vehicle repository shall also maintain a `FIRMWARE_VERSION` file or equivalent metadata documenting the firmware and onboard computer versions that were flight-tested:

```
# FIRMWARE_VERSION
# This file documents the firmware and onboard computer configuration
# that has been flight-tested for this vehicle.

# Flight Controller Firmware
CEREBRI_VERSION=v2.1.0
ZEPHYR_VERSION=v3.5.0
BOARD=mr_canhubk3

# Onboard Computer
ONBOARD_COMPUTER=navqplus
UBUNTU_VERSION=22.04
ROS_DISTRO=humble
CRANIUM_VERSION=v1.0.0

# Flight Test Information
FLIGHT_TEST_DATE=2026-01-15
```

This allows:
- Vehicles to remain on stable, known-good versions
- Middleware to continue evolving without breaking vehicles
- Clear upgrade paths when vehicles are ready to update

### Migration Path

The migration shall proceed in phases:

#### Phase 1: Repository Creation
1. Create individual vehicle repositories
2. Copy existing vehicle code from Cerebri `app/` folder
3. Set up CI infrastructure for each vehicle

#### Phase 2: Cerebri Cleanup
1. Remove vehicle-specific code from Cerebri
2. Create the minimal reference application
3. Update Cerebri CI to focus on middleware validation

#### Phase 3: Driver Consolidation
1. Reabsorb `zros_drivers` repository back into Cerebri
2. Consolidate all remaining driver code into Cerebri
3. Archive the `zros_drivers` repository
4. Update Spinali to depend on Cerebri instead of `zros_drivers`
5. Cerebri becomes the unified middleware layer with all ZROS drivers

#### Phase 4: Documentation and Tooling
1. Update all documentation to reflect new structure
2. Create tooling to simplify vehicle repository setup
3. Establish guidelines for vehicle maintainers

## Rationale

### Why Separate Repositories?

**Git submodules were considered** but rejected because:
- They add complexity to the development workflow
- Version pinning is harder to manage correctly
- CI configuration becomes more complex

**Monorepo with directories was considered** but rejected because:
- Still couples vehicle and middleware releases
- CI still runs for all vehicles on every change
- Doesn't solve the version pinning problem

**Separate repositories were chosen** because:
- Clean separation of concerns
- Each repository has its own release cycle
- Version pinning is explicit and straightforward
- CI is focused and efficient
- Matches the actual development cadence (middleware fast, vehicles slow)

### Why Reabsorb zros_drivers into Cerebri?

The `zros_drivers` repository was originally created to separate driver code from middleware. However, in practice:

- **Tight coupling**: ZROS drivers and Cerebri middleware are tightly coupled and typically need to be updated together
- **Version coordination burden**: Maintaining compatible versions across two repositories adds complexity
- **No clear benefit**: The separation doesn't provide meaningful modularity since drivers can't be used without Cerebri
- **Single point of testing**: Both need to be tested together anyway, so a single repository simplifies CI

Consolidating into a single repository reduces maintenance burden and simplifies the dependency graph for vehicle repositories.

### Why Non-Blocking Vehicle CI?

The daily vehicle CI is intentionally non-blocking because:

1. **Flight testing is the real validation**: Automated builds can't validate that a vehicle is safe to fly
2. **Middleware shouldn't wait**: Core middleware improvements shouldn't be blocked by vehicles that haven't been updated yet
3. **Clear responsibility**: Vehicle maintainers are responsible for their vehicles, not middleware developers
4. **Realistic expectations**: Some vehicles may intentionally stay on older middleware versions

### Why Require Flight Test for Vehicle PRs?

Main branch code will be used by others building the same vehicle. Without flight test validation:
- Users could build and fly untested code
- Regressions could cause crashes or unsafe behavior
- Trust in the project would erode

Flight testing is the minimum bar for safety-critical vehicle code.

## Backwards Compatibility

This change significantly restructures the codebase. The following compatibility concerns apply:

### For Existing Users

- Users with existing Cerebri checkouts will need to migrate to the new structure
- Build commands and paths will change
- Documentation will be updated with migration guides

### For Vehicle Developers

- Existing vehicle code will need to be adapted to the new repository structure
- Dependencies will need to be explicitly declared
- CI configuration will need to be set up

### Mitigation

- Detailed migration guides will be provided
- The old structure will be maintained in a branch for reference during transition
- Tooling will be provided to help automate the migration

## Reference Implementation

The reference implementation will be tracked in the following locations:

1. **Cerebri Middleware**: [cognipilot/cerebri](https://github.com/cognipilot/cerebri) (to be refactored)
2. **Vehicle Template**: A template repository for creating new vehicle repos
3. **Migration Scripts**: Tooling to help migrate existing vehicles

Implementation PRs will be linked here as they are created.

## Open Questions

1. **Shared vehicle code**: If multiple vehicles share significant code (e.g., multirotor control logic), should there be a shared library repository?

2. **Hardware-in-the-loop testing**: Can we develop HIL testing infrastructure that reduces reliance on actual flight testing for basic validation?

3. **Release coordination**: How do we communicate to users which middleware/vehicle version combinations are known-good?
