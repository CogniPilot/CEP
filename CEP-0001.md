## Abstract

This CEP describes the purpose of CogniPilot Enhancement Proposals (CEPs), their types, workflow, and the format requirements for authoring them. CEPs are the primary mechanism for proposing major new features, collecting community input on design decisions, and documenting the rationale behind significant changes to CogniPilot.

## What is a CEP?

CEP stands for CogniPilot Enhancement Proposal. A CEP is a design document providing information to the CogniPilot community, or describing a new feature, architectural change, or process for CogniPilot and its ecosystem.

The CEP process is inspired by Python's PEP process and ROS's REP process. The goal is to provide a structured way to:

1. Propose significant changes to CogniPilot
2. Collect community feedback before implementation
3. Document design decisions and their rationale
4. Build consensus within the community

## CEP Types

There are three types of CEPs:

### Standards Track

Standards Track CEPs describe new features or significant implementation changes to CogniPilot components such as:

- Cerebri middleware
- Vehicle applications
- Synapse communication protocols
- ZROS drivers and interfaces
- Build system and tooling

### Informational

Informational CEPs describe design guidelines, best practices, or provide general information that does not propose new features. These CEPs do not require community consensus but should be accurate and useful.

### Process

Process CEPs describe procedures, workflows, or changes to the CogniPilot development process. This includes changes to decision-making processes, development workflows, and tools used in CogniPilot development. This CEP (CEP-0001) is an example of a Process CEP.

## CEP Workflow

### 1. Idea Phase

Before writing a CEP, the idea should be discussed informally with the CogniPilot community. This can be done through:

- GitHub Discussions
- Community chat channels
- Direct communication with maintainers

The goal is to validate that the idea is appropriate for a CEP and gather initial feedback.

### 2. Draft Phase

Once the idea has been vetted, the author writes a draft CEP following the format specified in this document. The draft is submitted as a pull request to the CEP repository.

The CEP editors will:
- Assign a CEP number
- Review the CEP for format compliance
- Set the initial status to "Draft"

### 3. Discussion Phase

The draft CEP is discussed by the community. The author should:

- Respond to feedback and questions
- Update the CEP based on discussion
- Build consensus around the proposal

### 4. Decision Phase

For Standards Track CEPs, the CogniPilot maintainers make the final decision to accept or reject the proposal. The decision is based on:

- Technical merit
- Community consensus
- Alignment with CogniPilot's goals
- Implementation feasibility

### 5. Implementation Phase

Accepted CEPs move to implementation. The CEP should be updated to track implementation progress and reference the relevant pull requests.

## CEP Status Values

| Status | Description |
|--------|-------------|
| Draft | CEP is under active discussion |
| Active | CEP is an ongoing process document (like this one) |
| Accepted | CEP has been approved for implementation |
| Rejected | CEP has been rejected by maintainers |
| Withdrawn | CEP has been withdrawn by the author |
| Final | CEP has been fully implemented |
| Superseded | CEP has been replaced by a newer CEP |

## CEP Format

CEPs are written in Markdown format. Each CEP must contain the following sections:

### Header Table

Every CEP must begin with a metadata table containing:

| Field | Required | Description |
|-------|----------|-------------|
| CEP | Yes | The CEP number (assigned by editors) |
| Title | Yes | Short, descriptive title |
| Author | Yes | Name(s) of author(s) |
| Status | Yes | Current status |
| Type | Yes | Standards Track, Informational, or Process |
| Created | Yes | Date created (YYYY-MM-DD) |
| Requires | No | CEP numbers this CEP depends on |
| Replaces | No | CEP number this CEP replaces |
| Superseded-By | No | CEP number that replaces this CEP |

### Abstract

A short (~200 word) description of the technical issue being addressed.

### Motivation

The motivation section should clearly explain why the existing situation is inadequate and what problem the CEP solves. A CEP without sufficient motivation may be rejected.

### Specification

The technical specification should describe the syntax and semantics of any new feature in sufficient detail for implementation.

### Rationale

The rationale section should flesh out the specification by describing what motivated the design and why particular design decisions were made.

### Backwards Compatibility

All CEPs that introduce backwards incompatibilities must include a section describing these incompatibilities and their severity. The CEP must explain how the author proposes to deal with these incompatibilities.

### Reference Implementation

For Standards Track CEPs, the reference implementation section should link to or describe the implementation once available.

### References

Any external references or related documents.

## CEP Numbering

CEP numbers are assigned sequentially by the editors. The following ranges are reserved:

- 0001-4999: General CEPs
- 5000-5999: Vehicle-specific CEPs
- 6000-6999: Hardware/driver CEPs
- 7000-7999: Protocol/communication CEPs

## CEP Maintenance

The author of a CEP is responsible for maintaining it. This includes:

- Updating the CEP based on feedback
- Tracking implementation progress
- Marking the CEP as Final when complete

CEP editors may update CEPs for minor formatting or typographical corrections.

## CEP Editors

CEP editors are responsible for:

- Assigning CEP numbers
- Reviewing CEPs for format compliance
- Managing the CEP repository
- Updating CEP status
